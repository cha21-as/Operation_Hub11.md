# ADR-001: Store Request Status as an Event History, Not a Single Field

## Problem

`product-spec.md` requires that both the employee and the department be able to see the status of a request, and that the system remain explainable and auditable. A single "current status" field on a `Request` cannot show how or when a request got there — it can only show where it is right now.

## Options

1. **Overwrite current status** — each `Request` has one mutable `status` field that gets overwritten on every change.
2. **Keep status events** — each status change is recorded as its own immutable `StatusEvent`, and "current status" is derived as the latest event.

## Decision

**Keep events, not just current status.** Every transition (`Submitted → Awaiting approval → Approved → In progress → Resolved`, etc.) is written as a new `StatusEvent` row with an actor and a timestamp. The `Request`'s "current status" is computed as the most recent event, never stored as a second, separately-editable field.

## Consequence

This means more data and slightly more query complexity (status requires a lookup of the latest event rather than a single field read) — but it directly satisfies the spec's requirement for visible, explainable status, supports the audit requirement identified while hunting contradictions, and avoids two sources of truth ever disagreeing about a request's state.
